## 프로젝트 소개

수원대 학생이 학번·학과와 이미 들은 과목을 넣으면 졸업까지 무엇이 부족한지 계산하고, 공강 요일과 수업 시간대, 강의실 이동까지 따져 이번 학기 시간표를 최대 3안 짜 주는 웹 서비스입니다. 빈 강의실, 학사일정과 D-day, 강의평도 함께 볼 수 있습니다.

시간표를 짤 때는 수업 시간뿐 아니라 졸업요건, 이수 학점, 공강 선호, 강의실 사이 이동거리를 함께 따져야 합니다. 학생이 손으로 하던 이 계산을 서비스가 대신합니다.

## 담당 역할

- **데이터 모델** 학교의 실제 개설강좌 데이터에 맞게 강좌 스키마를 다시 설계하고, 마이그레이션(Alembic)을 도입했습니다.
- **데이터 적재** 개설강좌, 건물, 강의실, 졸업요건을 JSON 시드로 넣는 스크립트를 작성했습니다.
- **API** 아이디 방식의 가입·로그인, 학과 목록, 캠퍼스 건물과 도보 경로 API를 만들었습니다.
- **배포** 로컬 설치 스크립트와 팀 서버 배포 스크립트를 작성했습니다.
- **팀원 작업** 서버의 계층 구조와 인증, 추천 엔진의 원형, 화면 대부분.

## 사례 1 · 학교의 실제 데이터에 맞지 않던 강좌 모델

- **문제** 처음 만든 강좌 모델로는 수원대 개설강좌 데이터를 담을 수 없었습니다. 같은 과목코드에 분반이 여러 개 있고, 토요일 이러닝 강의가 있고, 강의 하나가 여러 강의실과 요일에 걸쳐 있었습니다.
- **원인** 모델이 과목 하나를 행 하나로 가정했습니다. 요일에 토요일이 없었고 교시는 9교시까지였습니다.
- **해결** 과목코드와 분반을 합친 값을 기본 키로 바꾸고 (과목코드, 분반) 유일 제약을 추가했습니다. 요일과 교과구분을 실제 데이터에 맞게 넓히고, 이 상태를 Alembic의 기준 마이그레이션으로 만들었습니다. 데이터 적재는 JSON 시드로 통일했습니다.
- **결과** 851과목, 1,617분반을 적재했습니다.

## 사례 2 · 팀 서버 배포 자동화

- **문제** 설치 스크립트에서 DB 초기화가 끝나기 전에 시드가 실행돼 실패했습니다. 팀 서버 배포는 여러 단계를 손으로 해야 했고, 다시 실행하면 프로세스가 중복으로 실행됐습니다.
- **원인** `mysqladmin ping`은 서버 프로세스가 응답하는지만 확인하고, 사용자와 DB 생성이 끝났는지는 확인하지 않습니다.
- **해결** 대기 조건을 실제 접속 성공(`SELECT 1`)으로 바꿨습니다. 팀 서버용 배포 스크립트를 만들어 DB와 계정 생성, 환경 파일 생성, 마이그레이션, 시드, 서버 실행, 헬스체크, 터널 주소 확인을 한 번에 처리했습니다. 다시 실행하면 기존 프로세스를 정리하고, DB가 비어 있을 때만 시드를 넣습니다.
- **한계** 프로세스가 종료되면 자동으로 다시 실행되지 않고, CI/CD는 없습니다.
