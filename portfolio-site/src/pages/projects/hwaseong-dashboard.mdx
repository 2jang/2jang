## 프로젝트 소개

화성시에서 버스가 부족한 지역을 찾고, 대책을 넣었을 때의 효과를 미리 계산해 보는 대시보드입니다. 시청 교통정책 담당자가 쓰는 것을 전제로 만든 대회 출품작입니다.

승하차 기록만 보면 버스가 부족한 곳을 찾기 어렵습니다. 버스가 없어서 타지 못한 사람은 기록에 남지 않기 때문입니다. 이 대시보드는 실제 승차 기록과 거주 인구로 추정한 잠재 수요를 합쳐 수요로 보고, 운행 횟수와 정류장까지의 거리로 공급을 계산합니다. 화성시를 1km 격자 786칸으로 나누고, 시간대(출근·낮·퇴근·심야)와 평일·주말별로 수요와 공급의 차이를 보여 줍니다.

## 담당 역할

- **백엔드** 공개 API 서버의 기본 구조와 AI 연동 기능, 관리자 API 전체, Docker 이미지. 공개 API 서버 파일의 57%, 관리자 API는 100%를 작성했습니다.
- **배포** 팀원이 만든 최초 배포 워크플로에 테스트 통과 조건과 헬스체크 검증을 추가했습니다.
- **프론트엔드** 서버 통신 계층, 지도 렌더 성능, 관리자 콘솔 화면을 담당했습니다(프론트엔드 코드의 32%).
- **팀원 작업** 데이터 수집과 격자 공간조인, 단위·API·E2E 테스트 체계, 초기 UI와 디자인, 프론트엔드 배포 구성(Cloudflare Pages).

## 구조

오프라인 파이프라인이 공공데이터를 격자 지표로 계산해 JSON으로 내보내고, FastAPI 서버는 시작할 때 이를 메모리에 로드해 응답합니다. 서버는 EC2 한 대에서 Docker Compose로 실행하고, Caddy가 HTTPS를 처리합니다. 프론트엔드는 Cloudflare Pages에 배포돼 이 API를 호출합니다.

요청은 메모리에 로드한 데이터로만 처리합니다. 배포는 테스트를 통과한 커밋에서만 시작되고, 새 컨테이너의 헬스체크가 통과해야 완료됩니다.

## 사례 1 · AI 호출 때문에 일반 조회 API까지 응답이 멈추던 문제 (백엔드)

- **문제** 챗봇과 보고서 요청이 몰리면 격자 조회 같은 일반 API까지 응답하지 않았습니다.
- **원인** AI SDK 호출이 동기 함수라 FastAPI의 스레드풀을 수십 초씩 점유했습니다. 다른 엔드포인트도 같은 풀을 나눠 쓰고 있었습니다. 앞서 넣었던 IP 레이트리밋은 같은 공유기를 쓰는 행사장 사용자까지 차단해서 제거한 상태였습니다.
- **해결** AI 경로만 `async`로 바꾸고 비동기 클라이언트를 프로세스당 하나만 만들어 재사용했습니다. 요청을 거절하는 대신 세마포어(동시 6건, 대기 25초)로 대기시키고, 대기 시간을 넘기면 오류 대신 안내 문구를 응답합니다. 주 프로바이더가 실패하면 다른 프로바이더를 대신 호출합니다.
- **결과** 동시 처리 수를 1로 제한하고 챗봇 6건이 대기하는 동안에도 일반 조회 API가 0.105초에 응답했고, 동시 12건이 모두 성공했습니다.

## 사례 2 · 관리자 재계산 후 서버가 재시작을 반복하던 문제 (백엔드)

- **문제** 지표 재계산 뒤 운영 중인 데이터 파일을 교체할 때 파일 하나가 목록에서 빠져 있었습니다. 새 기준 데이터와 이전 주말 지표가 섞였고, 서버 시작 시 검증에 실패해 재시작해도 계속 종료됐습니다.
- **원인** 산출 파일 목록을 수동으로 관리했고, 여러 파일의 교체가 원자적으로 처리되지 않았습니다.
- **해결** 재계산을 별도 스테이징 폴더에서 실행하고, 교체 전에 다른 프로세스에서 엔진을 실행해 새 산출물로 서버가 정상 시작되는지 먼저 검증합니다. 교체는 복사 후 `os.replace`로 하고, 중간에 실패하면 이미 바꾼 파일만 백업에서 되돌립니다. 마지막에 락을 잡고 메모리 스냅샷을 한 번에 교체합니다.
- **재발 방지** 스크립트 코드에서 출력 파일 목록을 추출해 교체 목록과 대조하는 테스트를 추가했습니다. 수정 전 코드에서는 누락된 파일명을 출력하며 실패합니다.
- **결과** 회귀 테스트를 CI에 포함했고, 파이프라인·API 테스트 173개가 통과합니다.

## 사례 3 · 실패해도 성공으로 표시되던 배포 파이프라인 (배포)

- **문제** 테스트와 배포 워크플로가 병렬로 실행돼서, 같은 커밋에서 배포가 테스트보다 2분 16초 먼저 성공으로 끝난 기록이 있었습니다. 배포 확인 요청은 아직 실행 중인 이전 컨테이너의 응답을 받아 통과했습니다. 컨테이너 헬스체크는 이미지에 없는 `curl`을 써서 항상 실패했습니다.
- **해결** 테스트가 성공했을 때만 배포가 시작되게 연결했습니다. 배포 스크립트는 오류가 나면 즉시 중단되게 하고, 새 컨테이너의 헬스체크가 통과할 때까지 최대 3분 기다린 뒤 공개 HTTPS 주소를 확인합니다. 헬스체크는 파이썬 표준 라이브러리로 바꿨습니다.
- **결과** 배포 작업이 새 컨테이너를 실제로 검증합니다. 무중단 배포는 아니어서, 컨테이너를 교체하는 동안 앱 시작 시간(15\~20초)만큼 서비스가 중단됩니다.

## 사례 4 · 지도 확대·이동 시 끊김 문제 (프론트엔드)

- **문제** 지도에서 마우스 호버, 이동, 휠 확대가 끊겼고, 정류장이 많은 구역에서 특히 심했습니다.
- **원인** 측정해 보니 지도 이동 시 프레임 처리 시간의 95%가 JS 실행이 아니라 화면을 다시 그리는 데(페인트) 쓰였습니다. 호버 강조에 쓴 `filter`가 지도 전체를 다시 그리게 했고, 휠 핸들러는 값을 쓴 직후 레이아웃을 읽어 강제 동기 레이아웃을 일으켰습니다.
- **해결** 호버 강조를 반투명 사각형 하나로 바꾸고, 정류장 이름표는 화면에 보이는 것만 그리고, 휠 배율은 프레임당 한 번만 적용했습니다.

| 지표 | 전 | 후 |
| --- | --- | --- |
| 호버 프레임 p95 | 118.5ms | 25ms |
| 확대 상태 팬 프레임 | 204ms | 105ms |
| 휠 12노치 처리(JS) | 1,065.5ms | 34.6ms |
| 화면에 그리는 이름표 | 2,866개 | 60개 |

## 프론트엔드·백엔드 연동

- **챗봇 스트리밍** 서버는 모델의 JSON 응답에서 답변 부분만 추출해 SSE로 전송하고, 클라이언트는 `fetch` 스트림으로 받아 데이터가 일정 시간 오지 않을 때만 타임아웃을 적용합니다. 서버와 클라이언트를 함께 구현했습니다.
- **지도 배경 정합** 카카오 지도와 격자가 확대할수록 어긋나던 문제를 투영 API로 아핀 변환을 계산해 보정했습니다. 정류장 위치 오차 중앙값이 890m에서 3m로 줄었습니다.
- **서버 주소 탐색과 보안 보완** 빌드 단계가 없는 정적 사이트라 환경별 서버 주소를 빌드 때 넣을 수 없었습니다. 그래서 실행 시 후보 주소를 순서대로 확인해 연결하도록 했습니다. 정적 호스팅은 없는 경로에도 200을 응답하므로, 상태 코드가 아니라 응답 내용으로 백엔드인지 판정합니다. 대회가 끝난 뒤 점검하다가, 사용자가 지정한 주소를 우선하는 규칙 때문에 관리자 토큰이 임의의 서버로 전송될 수 있다는 것을 발견했습니다. 허용 목록에 있는 주소만 받고 토큰도 허용된 주소에만 붙이도록 고쳤고, 회귀 테스트 36건을 추가했습니다.


## 회고

서버 상태가 프로세스 메모리와 로컬 파일에 있어서 워커를 1개로 고정했습니다. 트래픽이 늘면 상태를 외부 저장소로, 재계산을 작업 큐로 옮겨야 합니다. 본선에 진출하지 못해 EC2 서버는 현재 중단한 상태입니다.
