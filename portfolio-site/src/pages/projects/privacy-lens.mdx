## 프로젝트 소개

사진을 SNS나 단체 대화방, 중고거래에 올리기 전에 배경에 작게 찍힌 개인정보를 찾아 주는 웹 서비스입니다. 택배 송장, 신분증, 처방전, 모니터 화면처럼 찍을 때는 눈에 띄지 않던 정보를 찾아 어디에 있고 왜 위험한지 보여 주고, 사용자가 고른 영역을 가린 사진을 만들어 줍니다.

설치 없이 브라우저에서 쓰고, 휴대폰에서는 카메라로 바로 찍어 검사할 수 있습니다. 올린 사진과 OCR로 읽은 글자는 저장하지 않고 메모리에서만 처리합니다.

## 주제 선정과 엔진 채택

주제는 팀 회의에서 정했습니다. LLM API만 호출하는 프로젝트는 피하고, 전시회에서 관람객이 바로 써 볼 수 있으면서 실생활에도 쓸 만한 주제를 찾다가 나온 아이디어입니다.

사진을 확대하면 읽을 수 있는 글자까지 가려야 한다고 봐서, 객체 인식보다 OCR 성능이 더 중요하다고 판단했습니다. 그래서 분석 엔진을 두 명이 각자 만들어 성능이 좋은 쪽을 채택하기로 했습니다. 팀원은 EasyOCR로 기존 코드를 이어서 만들었고, 저는 PaddleOCR로 새로 만들었습니다. 제 엔진의 인식 성능이 더 좋아 팀 저장소에 반영했습니다.

## 담당 역할

- **분석 엔진** OCR, 판정 규칙, 가림 처리를 포함한 분석 엔진을 만들었습니다. 별도 저장소(privacy-lens-2)에서 개발해 팀 저장소에 반영했습니다.
- **신규 개발** 게이트웨이(대기열과 엔진 분산), 처리 시간 추정과 SSE 진행 표시, LLM 판단 모듈, CI.
- **배포·운영** 홈서버(미니PC)와 개인 PC에 게이트웨이와 엔진을 배포하고, Cloudflare Tunnel로 공개했습니다.
- **그 밖에** 화면의 API 호출 계층과 진행 표시를 담당했고, 학습 데이터 수집을 일부 도왔습니다.
- **팀원 작업** 프론트엔드 화면, 학습 데이터셋 구성, 객체 검출 모델(YOLO)의 학습·평가와 검출 연동, 판정 규칙 일부.

## 사례 1 · PaddleOCR 엔진의 동시 요청 오류

- **1단계, 요청 하나가 서버 전체를 멈춤** 엔드포인트가 `async def`였고, 몇 초씩 걸리는 OCR이 이벤트 루프를 점유했습니다. `def`로 바꿔 요청마다 스레드풀에서 실행되게 했습니다.
- **2단계, 동시 요청에서 엔진 오류** 요청이 병렬로 처리되자 두 요청이 같은 PaddleOCR 추론기를 동시에 사용했고, 서로의 중간 텐서를 덮어써 `Broadcast dimension mismatch`로 실패했습니다. 추론기가 스레드 안전하지 않았기 때문입니다. 엔진에 잠금을 걸어 한 번에 하나만 실행하고, 대기열로 순서를 관리했습니다.
- **3단계, 잠금이 있어도 Linux에서 실패** 동시 실행은 막았지만, 추론하는 스레드가 요청마다 바뀌는 것이 문제였습니다. 서버 시작 시 준비용 스레드에서 만든 엔진을 다른 스레드가 사용하면 `RuntimeError`가 발생했고, PaddleOCR 저장소에도 같은 증상이 보고돼 있었습니다. 엔진 생성과 추론을 전용 스레드 하나에 고정해 해결했습니다.
- **결과** PaddleOCR 추론기는 한 번에 하나, 항상 같은 스레드에서만 안전하다는 것을 확인했습니다. 스레드 일치, 동시 요청, 실패 후 복구를 테스트로 검증합니다. 추론이 실패하면 503과 `Retry-After`를 응답하고 엔진을 다시 생성합니다.

## 사례 2 · 측정 결과로 결정한 확장 구조: 게이트웨이와 엔진 N대

- **과제** 동시 사용자가 늘면 대기가 길어집니다. 한 서버 안에서 OCR 작업자를 늘릴지, 서버를 늘릴지 결정해야 했습니다.
- **측정** 엔진 하나가 이미 CPU를 98\~100% 사용했습니다. 작업자를 4개로 늘려도 처리량은 최대 31%(큰 사진은 11%)만 늘었고, 한 장당 처리 시간은 작업자 수만큼 길어졌습니다. 스레드를 10개에서 16개로 늘려도 결과는 같았습니다.
- **설계** 컴퓨터 한 대에서는 엔진을 하나만 실행하고, 컴퓨터를 늘리는 쪽을 택했습니다. 원래 한 서버에 있던 프론트엔드와 백엔드를 게이트웨이와 엔진으로 분리했고, 화면은 자원을 거의 쓰지 않아 게이트웨이가 함께 제공합니다. 게이트웨이가 대기열 하나를 관리하고, 유휴 엔진에 요청을 한 건씩 배정합니다. 요청 ID마다 담당 엔진을 고정해 진행 상황 조회와 취소 요청이 같은 엔진으로 전달됩니다.
- **장애 처리** 엔진 상태를 5초마다 확인하고, 연결 거부는 즉시, 늦은 응답은 2회 연속일 때 제외합니다. 재시도는 처리 시작 전의 연결 실패에만 적용합니다. 같은 사진이 두 번 처리되는 것을 막기 위해서입니다.

## 사례 3 · 사진 한 장 처리 시간 단축

- **문제** 홈서버(N100 미니PC)에서는 사진 한 장을 처리하는 데 1분이 넘게 걸렸습니다. 그동안은 기능 개발과 정확도가 우선이어서 미뤄 두었고, 전시회 3일 전에 속도 개선을 시작했습니다.
- **엔진 서버 교체** 게이트웨이와 엔진이 분리돼 있어서, 화면과 게이트웨이는 홈서버에 두고 엔진만 성능이 좋은 서버로 옮길 수 있었습니다. CPU만 바꿔도 약 20초로 줄었습니다.
- **GPU 전환** PaddleOCR과 YOLO 모두 GPU 버전이 있어 GPU에서 실행하도록 바꿨습니다. 설치 검사(pip check)는 통과하는데, 실행하면 PaddleOCR과 PyTorch가 한 프로세스에서 함께 로드되지 않았습니다. Windows에서는 두 라이브러리가 서로 다른 cuDNN 버전을 고정해 DLL이 충돌했고, Linux에서는 NCCL 패키지 두 개가 같은 파일을 덮어쓰고 있었습니다. 두 라이브러리를 CUDA 13 빌드로 맞춰 해결했습니다. RTX 5070에서 모델 로드 후 한 장 분석에 1.3초가 걸립니다.
- **판단 모델 교체** OCR과 객체 검출이 1초대로 줄자, 이번에는 사진당 수 초가 걸리는 LLM 판단이 병목이 됐습니다. 판단의 입출력이 정해진 JSON 형식이라 문장을 생성하는 모델이 꼭 필요하지 않다고 보고, 항목별 확률만 반환하는 Gemini Decision API를 적용했습니다.
- **판단 품질 보완** 처음 적용했을 때는 소품 사진 7장에서 개인정보가 아닌 항목을 13개 잘못 표시했습니다. 세 가지를 고쳐 0개로 줄였습니다.
    - "라벨이나 제목만 있는 조각인가"를 묻는 질문을 추가해, 라벨 자체를 개인정보로 표시하던 오류를 없앴습니다.
    - 여러 조각으로 끊겨 읽힌 카드번호를 묶는 일은 모델에 묻지 않고 기존 규칙 코드에 맡겼습니다.
    - OCR 신뢰도가 낮은 조각은 모델의 확신이 높을 때만 표시하도록 했습니다.
    - 놓침을 줄이려고 애매한 항목을 "확인 필요"로 올리는 보정 규칙도 시험했지만, 잘못 표시가 65개까지 늘어 적용하지 않았습니다.
- **결과** 판단 시간이 사진당 약 11초에서 약 1초로 줄었습니다. N100에서 1분이 넘던 전체 처리 시간은 GPU와 Decision을 함께 쓰면 2초 이내입니다. <Todo>측정 조건 기록 필요</Todo> 판단 품질 수치는 소품 사진 7장을 보며 조정한 결과라, 새 사진으로 다시 검증해야 합니다.

## 사례 4 · 재시도로 생기던 400 오류와 멱등 처리

- **문제** 운영 서버 로그에 "이미 대기열에 있는 번호표"(요청 ID 중복)라는 400 오류가 기록됐습니다.
- **원인** 브라우저는 요청을 한 번만 보냈는데 서버 로그에는 같은 요청이 두 번 기록돼 있었습니다. 서버 시작 직후 첫 요청이 엔진 초기화로 지연되자, 중간에 있는 Cloudflare가 요청을 다시 보낸 것으로 추정했습니다.
- **해결** 요청 ID가 같고 사진·설정 해시도 같을 때만 첫 요청의 결과를 기다렸다가 반환합니다. 요청 ID만 아는 다른 사용자는 결과를 받을 수 없습니다. 게이트웨이에도 같은 규칙을 적용했습니다.

## 사례 5 · 운영에서만 나던 500 오류

- **문제** 원격 서버에서는 사진이 아닌 파일을 올리면 400 대신 500이 발생했고, 로컬에서는 재현되지 않았습니다.
- **원인** 서버 로그에 `ModuleNotFoundError: No module named 'pi_heif'`가 남아 있었습니다. 이를 추적해 보니, YOLO 라이브러리가 import되는 순간 `PIL.Image.open`을 자체 함수로 교체하고 있었습니다. 로컬 테스트는 YOLO를 불러오기 전에 실행돼서 문제가 드러나지 않았습니다.
- **해결** YOLO를 불러온 직후 원래 함수로 되돌리고, 재현 테스트를 추가했습니다. 이 테스트는 수정 전 코드에서 같은 오류로 실패합니다.

## 회고

게이트웨이의 대기열과 엔진 목록은 메모리에만 있습니다. 게이트웨이가 종료되면 대기 중인 요청이 사라지므로, 다음 단계는 대기열을 외부 저장소로 옮기는 것입니다. 배포는 아직 수동이고 Docker 구성이 없습니다.

가장 오래 걸린 일은 학습 데이터셋을 모으는 것이었습니다. 개인정보를 다루는 주제라 실제 신분증이나 문서를 쓸 수 없어서, 가상 정보로 만든 자료를 직접 촬영해 데이터셋을 구성했습니다.
